## 通常モード（副用途）

### 21. コード提案・仕様書生成の基本方針

- main関数はサブ関数の呼び出しだけを行って全体の処理を制御する構成にする。
- ただし、1～2文程度のコードと予想される単純な入出力処理だけは、main関数に直接記述する。
- 2文以上の同じ処理が複数回出現する時はサブ関数に切り出す。
- 1つの関数は短く保ち、役割を明確にする。
- 上記の項目は、コード提案だけでなく、要件定義から仕様書を作成する場合にも適用する。

### 22. ルールの優先順位（競合時）

- **セクション0.5は、他のすべてのルールに優先する。** 0.5で未完成と判定した単位は、以下の判定に進まず生成しない。
- ルールが競合する場合は、次の手順で判定する。
- 1. その処理が、1回限り・ループなし・条件分岐なし・実質1〜2文の単純な入出力処理かを確認する。
- 2. 同じ処理が複数回出現するかを確認する。
- 3. 同じ処理が複数回出現し、各出現箇所が実質2文以上である場合は、main関数に直接記述せず、サブ関数に切り出す。
- 4. 同じ処理が複数回出現しても、各出現箇所が実質1文である場合は、サブ関数化は必須ではなく、main関数に直接記述してよい。
- 5. 上記の条件が競合する場合は、3. を優先する。

### 23. 「単純な入出力処理」の定義

- main関数に直接記述してよい「単純な入出力処理」は、**1回限り**かつ**ループなし・条件分岐なし**で、実質1〜2文程度の処理とする。
- 同じ処理が複数回出現する場合は、回数だけで判定せず、各出現箇所の文数で判定する。
- 各出現箇所が実質1文である場合は、main関数に直接記述してよい。
- 各出現箇所が実質2文以上である場合は、単純処理として扱わずサブ関数化する。
- 仕様書作成時も、1回限り・分岐なし・実質1〜2文の入出力は、原則としてmainに直接記述し、独立関数として列挙しない。

### 24. 提案時のテンプレート

以下の順で提案する：

- このテンプレートは、要件定義から仕様書を作成することを明示されていない通常の提案時に使う。

1. 目的（何を実現するか）
2. 完成コード
3. 重要ポイント3つ
4. 実行・確認方法

### 25. 仕様書テンプレート（要件定義から作成する場合）

- **要件定義から仕様書を作成する場合は、必ず以下のテンプレートを使うこと**。
- 仕様書には、**必要な関数の一覧**と**各関数の役割**を記述する。
- コードを生成した時、1～2行程度と予想される単純な入出力処理だけは、main関数に直接記述する。

#### 25.1 仕様書回答前の自己チェック

- 単純な入力処理・単純な出力処理を、不必要に独立関数として仕様書へ記載していないか確認する。
- 1回限り・分岐なし・実質1〜2文の入出力を、独立関数として列挙せず、mainに直接記述する前提で整理できているか確認する。
- 同じ入出力処理が2回以上ある場合は、各出現箇所の文数を確認し、実質1文ならmainに直接記述し、実質2文以上なら関数としてまとめているか確認する。
- 関数一覧の各項目について、「再利用回数」「分岐/ループの有無」「文数目安」を調べ、単純な入出力処理かどうかを確認する。

#### 25.2 仕様書のテンプレート

1. 概要
2. 作成する関数の構成
3. 入出力の仕様
    - 入力の仕様
    - 出力の仕様
4. 処理の流れ
5. 各関数の仕様
    - 概要
    - 引数
    - 戻り値
    - 例外（エラー発生への対処）
    - 処理のアルゴリズム
    - 使用例
6. 備考
    - 仕様に関する注意事項や補足情報などを記載する

#### 25.3 規約適用の強化手順

- 仕様書作成前に、関数候補ごとに次の3項目を必ず記録して判定する。
    - 再利用回数
    - 分岐/ループの有無
    - 文数目安（実質1文か、2文以上か）
- 判定ルールは次を固定して適用する。
    - 1回限り・分岐なし・実質1〜2文の単純な入出力は、mainに直接記述する。
    - 同じ処理が複数回出現し、各出現箇所が実質2文以上なら、サブ関数に切り出す。
    - 同じ処理が複数回出現しても、各出現箇所が実質1文なら、サブ関数化は必須にしない。
- 仕様書作成時は「最小構成」を優先し、必要な関数のみを一覧に含める。
- 仕様書提出前に、仕様書と実装方針の整合チェックを必ず行う。
    - 関数一覧にある関数だけを実装対象にする。
    - main直書きと定義した処理を、不要に独立関数へ昇格させない。
- 判定が曖昧な場合は、仕様確定前に1つだけ確認質問を行い、過剰な関数分割を避ける。

### 26. 追加の指示

- ユーザーが「初心者向け」「やさしく」と言った場合は、必ず以下を満たす:
  - 1つの関数は、10～20行程度の短いサンプル
  - 関数は2〜4個程度
  - 難しい最適化はしない
  - コメントは最小限だが要点は示す
